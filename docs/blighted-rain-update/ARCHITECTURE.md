# 污秽之雨更新 · 架构接入约定

本文件基于 1.0 实际源码与 [统一开发指南](../MOD_DEVELOPMENT_GUIDE.md)、[代码规范](../CODE_STANDARDS.md)、[附属 API v1](../ADDON_API.md)。以下保留准备阶段的设计约束；第一部分的实际分层与实现见 [实现记录](PART_1.md)。

## 最小接入

两版 `PurifiedUndead` 构造器各调用一次 `BlightedRainContent.register(modBus)`。它与 `SlateContent`、`FoundryContent` 一样是模块注册边界；第一部分入口安装专属加载器事件适配；纯规则、存档、效果与客户端分层，不保存服务器引用。当前没有新物品或实体注册器。

未来新增的专属注册内容放在此模块注册入口，使用本体 `purified_undead` 命名空间。注册 ID 在第一次真实内容实现时确定；不预留无用途 ID。既有注册器和旧 ID 保持原位，避免为此次更新搬迁所有历史内容。

入口负责安装具体实现，不负责天气计算、伤害、发奖、资源加载或存档读写。模块之间直接调用已有明确职责的服务即可，不引入通用模块管理器、重复事件总线、服务定位器或只有单实现的接口体系。

## 依赖方向与复用

|实际需求出现后|接入方式|兼容边界|
|---|---|---|
|独立新内容注册|在 `BlightedRainContent` 内按实际类型创建加载器的 deferred register|仍使用本体 ID；不创建第二个 `@Mod`|
|服务端玩法|模块专属规则和游戏事件适配分开；计算复杂时沿用已有 `*Model` 的纯规则模式|事件层只处理对象筛选、上下文和结算；不往总入口堆业务|
|已有战士、契约奖励|使用现有 `WarriorRewardService`；需要与附属同样的显式授予语义时使用 `ProgressApi`|不能复制直接赠物、去重、pending、通知或死亡恢复逻辑；既有自然获取开关语义仍有效|
|已有进度查询和通知|`ProgressApi` / `ProgressSnapshot` / `ProgressChangedEvent`|主线程访问；通知回调不能同步重入修改；快照不等于当前佩戴|
|新类型奖励或独立进度|按已确认需求设计模块自己的状态与交付规则|不把新状态塞进八战士枚举或复用旧 NBT 键；新增存储须定义缺省、读写边界和迁移|
|合成、标签、亡灵兼容|原版数据、现有标签与 `UndeadCompatibility`|不复制已有识别名单；可选实体 `required:false`；标签合并 `replace:false`|
|铸造加工|复用 `FoundryRecipes` 已有配方及严格重载入口|不替换方块实体或绕过余料、输入方向和同步约束|
|客户端画面、输入|已有 `client/` 层与对应加载器客户端生命周期|公共入口不能引用 `Minecraft`、渲染器、屏幕等客户端类型|
|客户端动作与必要同步|经既有 `ModNetwork` 接入具体包|只传意图，服务端检查资格、目标、速率和冷却；编号及协议变化需同步两版|
|可选第三方支持|现有 `compat/` 中的专属桥接|延迟解析、缓存查找、明确降级；不使第三方成为本体核心反向依赖|

附属 `spirits_of_expand` 可以依赖本体公开 API；本体不得反向依赖附属入口或其源码。新包当前属于内部实现，不是公开扩展 API。没有确定的跨模组使用场景前，不扩展 API v1。

## 状态、生命周期与鲁棒性

只有真实功能需要时才建立配置、网络、持久化或缓存。玩家状态、维度状态和全服状态的所有者须按功能明确，不能默认放在静态全局集合。服务器主线程执行世界和库存写入；新增任务与缓存需要定义退出、死亡、换维度、服务器停止时的保留或清理策略。

继续保留现有边界：死亡界面不补发物品；真实交付成功才清 pending；重生不刷新已有冷却；客户端预测不决定命中；临时伤害上下文通过 `finally` 清理；属性修饰符身份稳定；实际消耗时再次核对物品、数量和当前装备。

如后续确认新增环境效果，先定义维度、触发对象、时间来源及适用范围，再选择对应事件。不得仅凭更新名称增加每刻全世界扫描或修改原版天气。资源、配方和配置需要有数量、长度边界；非法重载保留可用状态；不靠大范围捕获异常隐藏实现错误。

## 两版与验证

两版保持相同职责和语义，但各自使用 Forge / NeoForge 事件及注册 API。1.20.1 的 UUID、NBT、复数数据目录与 1.21.1 的 Holder、数据组件、ResourceLocation 修饰符、单数数据目录分别处理；不进行整目录覆盖。

每个具体功能完成后，根据受影响链选择有意义的规则测试和运行验证，并执行两版完整构建。运行验证必须确认游戏 `_OK` 标记且无相应失败标记。新视觉需要游戏内检查；新增或改动 Mixin 必须使用完整发布 JAR 检查正式加载器启动。测试仅放在 `src/test` / `src/smoke`，不能进入成品。

本阶段空入口不增加镜像实现的单元测试。以两版现有构建、服务端回归、附属加载检查、包内容和源码指纹核对验证接轨。以后引入实际规则时再补充针对边界与失败路径的测试。
